Crawl Flow · 从一条任务到一行数据

采集流程 全景图

整个系统只有一个任务类型——抓某个系列的某一页（type=page）。 播种器把它投进 Redis Stream，常驻 Worker 消费后抓页、清洗、幂等落库， 再沿“游标 + 追加锁”自动推进下一页，直到整个系列采完。 失败与崩溃则交给 PEL + XCLAIM 兜底。

阶段一：播种（bin/seed.php → Producer）

只在开始时跑一次，可 --force 重跑

发现系列

ApiClient::productTypes()

请求站点接口拿到该大类下的全部产品系列（分立元器件共 12+ 个）。

HTTP GET api.shikues.com/api/product/productType

圈定目标范围

Producer::select()

按 --types 1,3,4 精确指定，或未指定时按 id 升序取前 limit 个，避免误采全站。

系列元数据先落 MySQL

Db::upsertType()

写入 source_types（source + type_id 唯一）—— 即使任务还没跑，系列目录也已可见。

游标就绪 + 投首页任务

initCursor / addTask

初始化该系列游标 cur:{type_id}（status=pending，done_pages=0）， 然后 XADD 一条 {type:page, type_id, page:1} 到 tasks 流。

幂等跳过

已 done / 采集中

已完成的系列（status=done）跳过；采集中/待处理的系列不重复投递，避免任务堆积。 --force 则重置游标、清残留“追加锁”后重新投首页任务（用于重采）。

阶段二：Worker 主循环（bin/worker.php）

常驻进程：先接管失联，再读新消息

① 接管失联消息

RedisStore::claimBatch()

XPENDING tasks workers IDLE 30000 - + 5 找出超过 claim_idle 未 ACK 的消息 → XCLAIM 转移给自己重试 （日志带 (CLAIM) 标签）。崩溃恢复与失败重试都走这条路径。

② 阻塞读新任务

RedisStore::readBatch()

XREADGROUP GROUP workers {consumer} STREAMS tasks > 每轮最多 batch=5 条，阻塞 block_sec=5 秒。 消息进入 PEL（pending entries list），处理成功前不会消失。

③ 逐条 process()

抓页 → 清洗 → 落库 → 推进

见下方「单任务八步」。整轮 0 条处理则空转 +1，连续空转满 idle_rounds（0=永不退出）自动退出，适合守护进程拉起。

worker.php · 主循环（简化）
while (true):
    # 1) 接管超时未确认（崩溃/失败遗留）
    foreach store.claimBatch(me)          as item: process(item, claimed=true)
    foreach store.readBatch(me)           as item: process(item, claimed=false)
    # 空转计数超限则 break（0=常驻）

# 单任务：
process(item):
    # 断点守卫：page <= done_pages ? ack 跳过（重投防重）
    rows = Normalizer::toModelRows(api.productList(...))
    db.upsertModels(rows)                  # (source,model) 唯一键
    store.patchCursor(type_id, done_pages=page, total_pages, rows)
    store.ack(msgId); statIncr(page_done)
    # 未到末页 && tryLockNextPage 成功 → XADD 下一页
C

单任务处理（Worker::process 的完整链路）

一个任务 = 抓一页型号数据

① 载荷校验 + 游标自愈

  • 非法载荷（非 page / type_id≤0）→ 直接 ACK 并转死信。
  • 找不到游标（绕过 seed 直投）→ 自动补建 cur:{type_id}。

② 断点守卫

游标 done_pages ≥ page 说明该页此前已成功 → 直接 ACK 丢弃。这是重投 / 并发重复消息的第一道去重闸。

③ HTTP 拉列表页

ApiClient::productList(type_id, page, 15)，附带 UA / Referer，超时 20s + 内置指数退避重试， 请求间隔 delay_ms=200 礼貌抓取。返回本页行与 last_page。

④ Normalizer 清洗

把站点行数据归一成落库模型：型号、封装、PDF、参数 JSON，兼容 不同系列字段异构。

⑤ 幂等落库

Db::upsertModels 按 (source, model) 唯一键 upsert， 同一型号无论重复处理几次，最终只有一行。

⑥ 推进游标

patchCursor：done_pages=当前页、total_pages=last_page、 rows 累计、到达末页或 max_pages 则 status=done（断点续采的依据）。

⑦ ACK 出 PEL

成功即 XACK 从消费组删除该消息，删除重试计数 attempt:{}， 统计 page_done / rows_upsert。

⑧ 追加下一页（闭环）

未采完则 加锁投递：SET addlock NX EX 60 抢到锁的实例 才 XADD page+1 —— 多 Worker 并发下每页只投一次。

为什么"翻页"交给 Stream 而不是 Worker 内 while 循环？ 每页都是独立任务，天然具备：中途宕机可从已推进的游标处续采； 多个系列 / 多页可被多 Worker 并行消费；单页失败只重试该页，不影响整链。
D

失败语义：重试 → 死信

at-least-once + 有限重试 + 死信可观测

任务产生XADD tasksseed 投首页 / Worker 投下一页
投递→
进入 PELXREADGROUP被某 consumer 读出后未 ACK 前均在此
成功→
完成XACK游标推进，统计 page_done
处理抛异常→
失败(第 n 次)不 ACKattempt++；留在 PEL
n<3 · claim_idle 后⟳ 接管XPENDING IDLE + XCLAIM
重试中…任意在线 Worker 接走重跑（日志 (CLAIM)）
n ≥ 3→
死信tasks:dead附 _dead_reason / _dead_at；游标置 dead
一个关键细节：失败≠任务丢失。 处理失败时 Worker 故意不 ACK，消息留在 PEL 中并标记重试次数； 超过 claim_idle（默认 30s，演示可设 CW_CLAIM_IDLE_MS=3000）后由其它 Worker 自动接管。 连续失败 max_attempts=3 次才转入 tasks:dead， 避免毒丸任务卡死整个队列，且失败全程可观测（stats.page_fail）。

崩溃恢复时序（XCLAIM 接管）

kill -9 之后，消息去哪了？

场景回放

  • t0：consumer wb 用 XREADGROUP 读走一批任务，开始处理（消息在 PEL）。
  • t0+3s：进程被 Stop-Process -Force 强杀——没有 ACK。
  • t0+3s+：stats.php 可见 PEL 未确认 > 0，任务“悬空”。
  • t0+claim_idle：新 consumer w2 的 XPENDING IDLE 定位到这批消息 → XCLAIM 转移 → 带 (CLAIM) 标签重跑。
  • 重跑后：游标守卫 + 唯一键 upsert 保证 MySQL 不重不漏，PEL 归 0。
崩溃恢复 · PowerShell 复现
# 1) 后台 worker 读走任务后强杀（模拟宕机）
$p = Start-Process php -ArgumentList 'bin/worker.php','--name','wb','--idle-rounds','0' -PassThru
Start-Sleep -Milliseconds 4000; Stop-Process -Id $p.Id -Force

# 2) 观察到遗留：PEL 未确认 > 0
php bin/stats.php

# 3) 新 consumer 自动接管（日志出现 (CLAIM)）
php bin/worker.php --name w2 --idle-rounds 0

[2026-09-05 12:19:28] INFO [4] p1/12 普通整流二极管(CLAIM)  写入 15 行，游标 page=1 total=12 rows=15
[最终状态] dead_letters=0 page_done=25 pending=0 rows_upsert=346
兼容性说明：实现未用较新的 XAUTOCLAIM（部分云 Redis 网关 / 低版本不支持）， 而以 XPENDING stream group IDLE ms - + N 定位 + XCLAIM 转移等价实现——两条命令均为 Redis 5.0 基础能力，兼容性最好。

运行总览与验证

stats.php 一键核对两层状态

stats.php · 演示实跑输出
[运行状态] dead_letters=0 page_done=27 page_fail=0 rows_upsert=376 stream_len=27 pending=0
[MySQL]    source_types=12 product_models=419

# 关键指标速读
pending      → PEL 未确认数，应为 0；>0 表示有消息在处理或"失联待接管"
dead_letters → 死信数，>0 需用 XRANGE tasks:dead 检查毒丸原因
rows_upsert  → 实际落库行数（去重后）
stream_len   → tasks 剩余任务数；归 0 且 pending=0 = 本轮采完
product_models → 结果行数；重跑不变 = 幂等生效
