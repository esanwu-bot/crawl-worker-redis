系统架构 采集流程 时序图
Runtime ↔ Adapter ↔ Redis / MySQL

一次采集的 时序图

整个系统只分两步：播种（seed.php 发现采集单元、建 Job、投首页任务） 与 消费（常驻 worker.php 循环取任务、调 Adapter 抓页、幂等落库、推进游标续采）。 Runtime 只在 adapters->get(payload.source) 一处分派数据源， 其余协议 / 字段 / 分页语义全部收敛在 Adapter 内。

参与方 Runtime · Adapter · Redis · MySQL · 数据源站点 可靠性 PEL + XCLAIM 幂等键 source+entity+unit_id+external_id
Runtime → Adapter（调用） Adapter → 数据源（HTTP） Runtime ↔ Redis Runtime → MySQL 返回 / 响应 失败 / 崩溃路径
1

播种时序（bin/seed.php → Producer）

只跑一次 · 可 --force 重跑

要点：播种阶段就把「采集单元目录」（source_types）与「作业」（crawl_jobs）落库， 并把每个单元的首个分页任务投进 Redis Stream。任务载荷是纯通用契约 {source, entity, operation, cursor, params}，Redis 对“采什么”完全无感知。
2

消费时序（bin/worker.php 常驻循环）

先接管失联，再读新任务

数据源无关的分派点：Runtime 仅在 adapters->get($payload['source']) 一处选择 Adapter； adapters 之后，抓取 / 解析 / 字段映射全部由 Adapter 完成，返回统一的 records[] + last_page，Runtime 一视同仁地落库、推进。
3

崩溃恢复时序（PEL + XCLAIM 接管）

kill -9 之后消息去哪了

为什么"不丢"

  • 消息先入 PEL：XREADGROUP 读出即登记，处理成功前不消失。
  • 崩溃不 ACK：进程被强杀时消息仍在 PEL，stats.php 可见 PEL > 0。
  • 超时即接管：任一在线 Worker 用 XPENDING IDLE + XCLAIM 接走重跑。

为什么"不重"

  • 断点守卫：游标 done_pages ≥ page 时直接 ACK 丢弃重复消息。
  • 幂等 upsert：唯一键 source+entity+unit_id+external_id，重复处理只更新不新增。
  • 结果一致：接管重跑后 MySQL 行数与游标完全一致。
兼容性：未使用较新的 XAUTOCLAIM（部分云 Redis 网关 / 低版本不支持）， 而用 XPENDING ... IDLE 定位 + XCLAIM 转移等价实现，两条命令均为 Redis 5.0 基础能力。
