PHP CLI Crawler · Redis Stream 版

元器件型号采集器
分层架构：任务在 Redis，结果在 MySQL

面向电子元器件站 shikues.com 的「系列 → 型号(行)」两层结构采集系统。 常驻 PHP 进程作 Worker，以 Redis Stream 消费组驱动任务，抓取、清洗后 幂等写入 MySQL；通过 PEL + XCLAIM 实现崩溃恢复与失败重试， 通过系列游标 Hash 实现断点续采。

运行形态 PHP 8.0+ CLI 常驻进程 任务队列 Redis 6.2+ Stream / 消费组 结果存储 MySQL 5.7+ 幂等 upsert 消费语义 at-least-once + 去重守卫 数据源 www.shikues.com 真实站点接口 可靠保障 断点续采 · 崩溃接管 · 失败重试 · 死信隔离

02

代码组件与职责

bin/ 编排脚本 + src/ 核心类

▸RedisStore.php

任务层封装：Stream 追加 / 消费组读 / XPENDING IDLE + XCLAIM 接管 / ACK / 游标 Hash / 追加锁 / 统计 / 一键重置。

▸Worker.php

常驻消费主循环与失败语义：接管→读→处理；失败消息留在 PEL，超 max_attempts 转死信，保证 at-least-once 与可观测。

▸Producer.php

播种：发现系列 → 元数据落 MySQL → 初始化游标 → 投递首页任务；支持 --force 重置游标重采。

▸ApiClient.php + Http.php

站点接口客户端：HTTPS 请求、超时与指数退避重试、请求间隔限速、证书降级策略（insecure_fallback）。

▸Normalizer.php

行数据清洗 → 落库模型：型号/封装/参数 JSON 归一化，异构兼容站点不同系列字段。

▸Db.php + Logger.php + bootstrap.php

MySQL 幂等 upsert 与计数、文件日志（logs/worker.log）、autoload 与 CLI 参数解析。

03

三大可靠性机制

每个语义都能在代码 / 演示中验证

1断点续采

每个系列一张游标 cur:{type_id} 记录已成功页数与总页数。Worker 每处理一页即推进游标； 重跑 / 重复投递时 断点守卫（page ≤ done_pages）直接 ACK 跳过，不重复抓取。

2崩溃恢复 / 失败重试

消息被读出后不立即删除，而是进入消费组 PEL。若 Worker 崩溃或处理失败未 ACK， 超过 claim_idle（默认 30s）即被任一在线 Worker 用 XPENDING IDLE → XCLAIM 接管重试。

3结果幂等

MySQL (source, model) 唯一键 upsert：同一型号无论被投递多少次，最终只有一行。 叠加 addlock 闸门保证“下一页任务”只投递一次。

4死信隔离

单条消息失败达到 max_attempts=3 即判定毒丸，写入 tasks:dead 并附死因， 对应系列游标置为 dead；不影响其余系列继续采集，事后可离线分析。

为什么用 Stream 而不是任务表 / 普通 List？ 消费组天然实现“同组消息不重复投递 + 负载均衡”，配合 PEL 使 “谁在处理、谁已死亡”可见可接管；而 List 方案的 LPOP 一旦取出即丢失， 任务表方案则需自研锁与扫描轮询。

05

MySQL 结果层

业务表全部落在 MySQL

⇥source_types 系列元数据

字段：source / type_id / type_name / type_name_en / extra(JSON)，唯一键 (source, type_id)。

播种即写入，任务还没跑也能看到系列目录。

⇥product_models 型号结果

字段：model / remote_id / package / pdf / specs_json(JSON) / source_url 等， 唯一键 (source, model)。

Worker 每页清洗后 upsert，可安全重跑。
